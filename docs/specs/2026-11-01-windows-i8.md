# I8 Windows — Vorlagen, Zugang, Active Directory, Failover-Cluster und SQL Server

**Status:** Entwurf 01.11.2026, **keine Umsetzungsfreigabe**. Erweitert Etappe I8 aus `2026-10-22-infrastruktur-vorhaben.md` (E4-W).

## 1. Auftrag (Owner 01.11.2026, Wortlaut sinngemäß)

- Derzeit gibt es keinen Windows-Server oder -Client außer den Geräten (Alfred-Satelliten). Alfred baut Windows selbst auf.
- Immer die **aktuellste Windows-Server-Version**; wählbar nach **Edition** (Standard / Datacenter) und **Ausprägung** (Core / mit Desktop). Dazu **Windows 11**.
- Alfred **lädt die Testversionen selbst herunter** (ISOs des Owners nicht nötig), ebenso die **VirtIO-Treiber**.
- Zugang: **OpenSSH von Windows** (wie vorgeschlagen), Alfred richtet es selbst ein.
- Ausbau: Alfred kann einen **Windows-Failover-Cluster** bilden und **SQL Server** installieren — **Einzelinstanz**, **Failover-Cluster-Instanz (FCI)** oder **Always-On-Verfügbarkeitsgruppe (AG)** — nach Best Practice.
- Nachtrag 01.11.: **SQL Server auch auf Linux**; **Domänencontroller als eigene Fähigkeit** (nicht nur als Unterbau für den Cluster); Alfred soll **weitere sinnvolle Windows-Fähigkeiten** erarbeiten, die der Owner nicht genannt hat (Abschnitt 3b).

## 2. Grundsätze

- Alles über freigegebene Changes (Motor), Geheimnisse nur im Tresor (Administrator-Kennwort, Domänen-Kennwörter, SQL-Dienstkonten, Lizenzschlüssel).
- Lesen ohne Rückfrage nur über eine **feste PowerShell-Leseliste** (wie bei Linux); alles andere braucht die Bestätigung.
- Testversionen sind zeitlich begrenzt (Server 180 Tage, Windows 11 Enterprise 90 Tage). Alfred führt das Ablaufdatum in der CMDB und meldet es rechtzeitig. Umstellung auf eine Lizenz (`DISM /Set-Edition` bzw. Produktschlüssel) ist ein eigener Change mit Schlüssel aus dem Tresor.
- Jede Fähigkeit wird live an einer Wegwerf-VM bewiesen, danach Stilllegung.

## 3. Etappen

### I8a — Windows-Vorlagen-Fabrik
- **Herunterladen:** aktuellste Server-Testversion und Windows-11-Enterprise-Testversion aus dem Microsoft Evaluation Center, VirtIO-Treiber-ISO (stabile Fassung von fedorapeople). Prüfsumme protokollieren; Version (Build) aus dem ISO lesen und in der CMDB führen. Neue Version → Vorlage (b) „neu bauen“.
- **Varianten:** Server × {Standard, Datacenter} × {Core, Desktop}; Windows 11 Enterprise. Gebaut wird nur, was verlangt wird (Parameter), nicht alle auf Vorrat.
- **Unbeaufsichtigte Installation:** Antwortdatei (`autounattend.xml`) auf einem eigenen kleinen ISO, wählt das Abbild nach Edition/Ausprägung, lädt VirtIO-Speicher- und Netztreiber, installiert Gast-Agent, aktiviert **OpenSSH-Server** (PowerShell als Standard-Shell), richtet Alfreds Schlüssel ein, aktiviert WinRM nur lokal.
- **Proxmox:** q35, OVMF (UEFI) mit EFI-Disk, **TPM 2.0** (Windows 11 Pflicht, Server empfohlen), VirtIO-SCSI, VirtIO-Netz, Ballooning aus.
- **Anpassung je Klon:** Cloudbase-Init (Gegenstück zu Cloud-Init): Rechnername, feste IP, Administrator-Kennwort aus dem Tresor, Alfreds Schlüssel; danach `sysprep /generalize` in der Vorlage. Neue VM: Fernzugang aktiv, CMDB-Eintrag, Käfig-Gegenstück siehe I8b.
- **Beweis:** je eine Probe aus Server Standard Core und Windows 11; SSH mit gepinntem Host-Schlüssel, Hostname, Gast-Agent, Ablaufdatum der Testversion in der CMDB.

### I8b — Windows-Zugang und lesende Analyse
- Fernzugriff erkennt Windows (PowerShell über SSH) und hat eine **eigene Leseliste**: `Get-ComputerInfo`, `Get-HotFix`, `Get-Service`, `Get-WindowsFeature`, `Get-SmbShare`, `Get-Volume`, `Get-Disk`, `Get-NetIPConfiguration`, `Get-NetFirewallProfile`, `Get-ScheduledTask`, Ereignisprotokoll-Fehler der letzten 24 h, installierte Programme (Registry, nur lesend), Cluster- und SQL-Status (I8d).
- **Käfig-Gegenstück:** ein **JEA-Endpunkt** (Just Enough Administration) nur mit diesen Befehlen; Lesen läuft dort, Ändern über das Administrator-Konto mit Bestätigung bzw. im Change.
- Sammler → CMDB (Server, Rollen, Dienste, Freigaben, Datenträger), Befunde → Problems; Windows-Updates im Anwendungs-Update-Bericht.
- **Beweis:** Bestandsbericht der Probe-VMs aus I8a.

### I8c — Active Directory als eigene Fähigkeit
- **Neuer Wald** oder **weiterer DC in einer bestehenden Domäne**; mindestens **zwei Domänencontroller** (Server Core) auf verschiedenen Proxmox-Hosts, integriertes DNS, Zeitquelle am PDC-Emulator (externe NTP-Quelle), bedingte Weiterleitung der AD-Zone im UniFi-DNS.
- Grundstruktur: OUs (Server, Clients, Dienstkonten, Admins), getrennte Admin-Konten (Tier-Modell light), Dienstkonten als **gMSA**, Kennwörter im Tresor; Papierkorb (AD Recycle Bin) an; DSRM-Kennwort im Tresor.
- Betrieb: FSMO-Übersicht, Replikation und DC-Gesundheit (`dcdiag`, `repadmin`) im Monitoring; **Systemstatus-Sicherung** der DCs und dokumentierte Wiederherstellung; Herabstufen/Stilllegen eines DC nur als Change.
- Optional: DHCP-Rolle mit Failover, Standorte/Subnetze.
- **Beweis:** zwei DCs, Replikation fehlerfrei, Mitgliedsserver beigetreten, Wiederherstellung eines gelöschten Objekts aus dem Papierkorb.

### I8d — Failover-Cluster und SQL Server (Windows)
- **Cluster:** Validierung (`Test-Cluster`) muss bestehen; Zeuge als **Dateifreigabe-Zeuge** (außerhalb der Clusterknoten); Knoten auf verschiedene Proxmox-Hosts (Anti-Affinität), eigenes Cluster-Netz optional.
- **SQL Server**, aktuellste Version (Testversion/Developer für Probe; Standard/Enterprise mit Lizenz aus dem Tresor für Produktion). Varianten:
  - **Einzelinstanz** — Ausgangspunkt.
  - **Always-On-Verfügbarkeitsgruppe (Empfehlung für Hochverfügbarkeit)** — kein gemeinsamer Speicher nötig; Standard-Edition = Basis-AG (2 Replikate, je eine Datenbank), Enterprise = volle AG; Listener im DNS.
  - **Failover-Cluster-Instanz** — braucht gemeinsamen Speicher; auf Proxmox nur über ein **iSCSI-Ziel** (eigene VM) sinnvoll; Storage Spaces Direct nur mit Datacenter.
- **Best Practice:** getrennte Datenträger für Daten/Log/TempDB (NTFS 64 KB), TempDB-Dateien je Kern (max. 8), max. Server-Arbeitsspeicher, MAXDOP/Kostenschwelle, Instant File Initialization, Dienstkonten gMSA, Firewall nur 1433/5022 aus erlaubten Zonen, Sicherungen (voll/differenziell/Log) auf das Sicherungsziel, Wiederherstellungstest.
- **Beweis:** AG mit zwei Knoten + Listener, geplanter Failover und zurück, Wiederherstellung einer Sicherung.

### I8e — SQL Server auf Linux
- Auf den von Microsoft für die jeweilige SQL-Version **unterstützten Distributionen** (Alfred prüft die Liste je Version; Vorlage aus der Fabrik passend wählen), Paketquelle von Microsoft, `mssql-conf` für Edition, Speicher, Pfade, TempDB, Agent; `mssql-tools` für Prüfungen.
- Varianten: **Einzelinstanz**; **Verfügbarkeitsgruppe mit Pacemaker** (Clustertyp EXTERNAL, Fencing, drei Knoten oder zwei + Konfigurationsreplikat) als Hochverfügbarkeit; Lese-Skalierung ohne Cluster (Clustertyp NONE) nur auf Wunsch.
- Gleiche Best Practice wie unter Windows (getrennte Datenträger, Speichergrenze, Sicherung + Wiederherstellungstest); Anmeldung per SQL-Konten aus dem Tresor oder AD (Keytab) wenn I8c vorhanden.
- **Beweis:** Einzelinstanz auf Linux, Sicherung und Wiederherstellung; danach AG mit Pacemaker und geplantem Failover.

## 3b. Weitere Windows-Fähigkeiten (Vorschlag Alfred/Claude, Owner wählt aus)

**Muss — ohne sie ist Windows-Betrieb nicht sicher:**
1. **Windows-Updates** als Standard-Change wie bei Linux: Wartungsfenster, Snapshot, Installation über den Windows-Update-Agenten, Neustart nur im Fenster, Cluster-bewusst (Knoten nacheinander, Rollen vorher verschieben), Nachher-Vergleich (Dienste, Rollen, Ereignisse). Ausstehende Updates im Anwendungs-Update-Bericht.
2. **Sicherheits-Grundlinie:** Microsoft Security Baseline per Gruppenrichtlinie (Domäne) bzw. lokal, **Windows LAPS** (eingebaut) für lokale Administratoren, SMBv1 aus, SMB-Signierung, TLS 1.0/1.1 aus, Firewall-Profile aktiv, Defender aktiv und aktuell, RDP nur mit NLA und nur aus Verwaltungszonen.
3. **Sicherung:** VSS-konsistente Proxmox-Sicherungen (Gast-Agent mit VSS), Systemstatus der DCs, SQL-Sicherungen; Wiederherstellungstest wie bei Linux.
4. **Überwachung:** Dienste, freier Speicher, Ereignisprotokoll-Fehler, Zertifikatsablauf, Ablauf der Testversion/Lizenz, Cluster- und AG-Zustand, Replikation der DCs → Lebenszeichen/Monitoring, Befunde → Problems.
5. **Lizenz/Aktivierung:** Aktivierungsstatus, Ablauf der Testversionen, Umstellung auf Lizenz per Change (Schlüssel aus dem Tresor).

**Sinnvoll:**
6. **Dateiserver:** Freigaben mit NTFS-Rechten nach Gruppen, Schattenkopien, Kontingente (FSRM), optional DFS-Namespace; Migration bestehender Freigaben (z. B. backupshare-Inhalte) als Change.
7. **Zertifikate:** interne PKI (AD CS) für Domänendienste und SQL-Verschlüsselung; öffentliche Zertifikate für IIS über Let’s Encrypt (win-acme), Erneuerung als Standard-Change.
8. **IIS/Webanwendungen** mit .NET-Hosting, Bindungen, Zertifikaten.
9. **Software-Verwaltung:** Inventar und Updates über **winget**, Anwendungs-Updates in den Bericht.
10. **BitLocker** mit TPM für Datenträger, Wiederherstellungsschlüssel im AD bzw. Tresor.
11. **Windows-11-Clients:** Domänenbeitritt oder Entra-Beitritt, Grundlinie, Software per winget.
12. **Import bestehender Windows-VMs** (VMware/Hyper-V/physisch → Proxmox): Disk-Import, VirtIO-Treiber nachrüsten, Gast-Agent — für künftige Übernahmen.

**Optional (nur auf Wunsch):**
13. **Entra Connect / Cloud Sync** mit dem bestehenden Microsoft-365-Mandanten — riskant für vorhandene Cloud-Konten, nur nach eigener Analyse und Owner-Entscheidung.
14. **Remotedesktop-Dienste** (Sitzungshost/Gateway) — Guacamole deckt den Fernzugriff heute ab.
15. **Druckserver**, **WSUS** (statt direkter Updates), **Hyper-V** — derzeit kein Bedarf erkennbar.
